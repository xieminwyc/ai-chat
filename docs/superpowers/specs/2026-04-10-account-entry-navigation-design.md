# AI Chat Account Entry Navigation Design

## 文档概览

| 项目 | 内容 |
| --- | --- |
| 文档主题 | 为 `/account` 与 `/settings` 增加首页可发现入口 |
| 当前阶段 | protected pages 落地后的第一轮导航接入 |
| 推荐方案 | 在工作台头部右上角已登录用户区增加账号操作带 |
| 设计目标 | 不打断聊天主流程，同时让用户能自然发现账号页与设置页 |

## 背景

项目已经具备：

- `/account` 页面，要求 `authenticated`
- `/settings` 页面，要求 `verified`
- `resolveProtectedPageAccess()` 服务端访问控制

但目前这两个页面只有“存在”，还没有“入口”。用户即使登录，也不知道它们已经可用。所以现在需要补一层非常轻的前端导航，把“服务端页面保护”接到“客户端可发现入口”上。

## 这次要解决什么

这次只解决：

1. 已登录用户能在首页工作台里自然看到 `/account`
2. 已验证用户能直接进入 `/settings`
3. 未验证用户能感知到 `/settings` 存在，但明确知道“验证邮箱后可进入”
4. 导航样式保持当前工作台视觉，不把聊天界面改成传统后台

这次**不**做：

- 顶部全站导航栏
- 左侧侧边栏重构
- 多级菜单或下拉菜单
- `/account` 与 `/settings` 的真实表单内容

## 推荐方案

### 方案 A：右上角账号操作带，我方推荐

做法：

- 在 `ChatApp` 的工作台头部右上角保留现有用户邮箱胶囊
- 在其后新增：
  - `Account`
  - `Settings`
  - `退出登录`
- 当用户未验证邮箱时：
  - `Account` 仍可访问
  - `Settings` 以弱化禁用样式显示
  - 附带短提示“验证邮箱后可进入 Settings”

优点：

- 最符合当前布局结构
- 与“当前用户是谁、能做什么”这组信息天然归在一起
- 不会和左侧聊天历史争夺层级

缺点：

- 页面入口偏操作型，不像完整站点导航

### 方案 B：左侧聊天栏顶部导航

优点：

- 更像工作台导航

缺点：

- 和聊天列表竞争注意力
- 在游客态和断开态下更容易显得突兀

### 方案 C：两处都放

优点：

- 发现率更高

缺点：

- 当前只有两个页面，容易显得重复
- 会让界面过早出现两套导航语义

### 推荐结论

采用方案 A。

## 视觉与交互规则

参考当前工作台已有风格和 `ui-ux-pro-max` 规则，这次导航要遵守：

- 使用现有浅色玻璃感面板语义，不额外引入深色工具栏
- 所有交互元素保持清晰 focus ring
- 触控目标不低于 `44px`
- hover 只做颜色与阴影反馈，不用 scale，避免布局抖动
- 未验证状态的 `Settings` 不是隐藏，而是保留一个禁用态可见入口

## 页面状态定义

### 已验证用户

- 显示邮箱胶囊
- 显示 `Account` 链接
- 显示 `Settings` 链接
- 显示 `退出登录`

### 已登录但未验证用户

- 显示邮箱胶囊
- 显示 `Account` 链接
- 显示弱化的 `Settings` 占位
- 显示“验证邮箱后可进入 Settings”短提示
- 显示 `退出登录`

### 游客或未登录用户

- 保持现有 `登录` / `注册` 区域，不新增 `/account` 与 `/settings` 入口

## 测试策略

聚焦在 `ChatApp` 头部行为：

- verified 用户能看到 `Account` 和 `Settings` 链接
- unverified 用户能看到 `Account` 链接，但 `Settings` 只以禁用文案形式存在
- 游客态不显示这两个入口

## 学习要点

这次导航接入最值得记住的是：

1. “入口可见性”和“页面保护”是两层职责
2. `/settings` 不该因为未验证就完全消失，否则用户感知不到产品边界
3. 把账号入口放在用户区，而不是聊天列表里，是在保护主工作流的注意力
