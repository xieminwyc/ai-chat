## 背景

当应用开始有了真实用户后，会面临这些问题：

1. **性能问题**：每次请求都查数据库，压力大
2. **安全问题**：恶意用户可以无限制调用接口
3. **体验问题**：某些操作（如发邮件）阻塞用户等待

Redis 缓存 + 限流是解决这些问题的经典方案。

## 本次设计目标

这份设计要解决 4 件事：

1. 理解 Redis 是什么、为什么需要它
2. 掌握基础的缓存策略（Cache-Aside）
3. 理解限流算法（令牌桶、滑动窗口）
4. 把这些能力应用到实际场景中

## 本次设计不做

- 不做 Redis 集群/哨兵（单机足够学习）
- 不做复杂的缓存预热策略
- 不做分布式锁（可以后续扩展）
- 不做消息队列（下一阶段）

## 方案设计

### 总体路线

```text
第一阶段：Redis 基础与缓存封装
  ↓
第二阶段：限流算法与实现
  ↓
第三阶段：应用到实际场景（登录/聊天）
```

### 为什么是这个顺序

1. **先缓存，后限流**：缓存理解了，限流就是基于缓存的计数器
2. **先基础，后应用**：先把工具造好，再用到业务里
3. **先单点，后扩展**：先跑通一个场景，再复制到其他地方

## 第一阶段：Redis 基础与缓存封装

### 这一阶段学什么

- Redis 是什么（内存数据库、键值存储）
- Redis 和 PostgreSQL 的区别
- 为什么需要缓存（减少数据库压力）
- Cache-Aside 模式（最常用的缓存策略）

### 为什么先做它

缓存是后端性能优化的基础。理解了缓存，后面的限流、分布式锁都好理解。

### 代码目标

- 安装 `ioredis` 客户端
- 创建 Redis 连接封装（单例模式）
- 实现基础缓存操作（get/set/delete/exists）
- 处理连接失败的情况（降级到直接查库）

### 要改/新增的文件

```
src/lib/
  redis.ts                    # Redis 客户端单例

src/server/cache/
  cache-service.ts            # 缓存服务封装
  cache-service.test.ts       # 测试

scripts/
  start-redis.sh              # 本地启动 Redis（可选）
```

### 怎么验证

- 写一个简单的缓存接口测试
- 验证缓存命中时确实没有查数据库
- 验证 Redis 挂掉时服务仍然可用（降级）

### 第一阶段完成后你应该懂

- Redis 和 PostgreSQL 的根本区别是什么
- Cache-Aside 模式的读写流程
- 为什么缓存要有过期时间
- 缓存穿透/击穿/雪崩是什么

## 第二阶段：限流算法与实现

### 这一阶段学什么

- 为什么需要限流（防刷、保护服务）
- 令牌桶算法（Token Bucket）
- 滑动窗口算法（Sliding Window）
- 两种算法的区别和适用场景

### 为什么接在缓存后面

限流本质上就是"基于时间的计数器"，而 Redis 正好适合存储这种计数器。

### 代码目标

- 实现令牌桶限流器
- 实现滑动窗口限流器
- 统一的限流检查接口
- 友好的限流错误提示

### 要改/新增的文件

```
src/server/rate-limit/
  rate-limiter.ts             # 限流器基类
  token-bucket.ts             # 令牌桶实现
  sliding-window.ts           # 滑动窗口实现
  rate-limit-error.ts         # 限流错误定义
```

### 怎么验证

- 写一个测试接口，快速调用看是否被限流
- 验证令牌桶的"恢复"机制
- 验证滑动窗口的时间精度

### 第二阶段完成后你应该懂

- 限流和并发控制有什么区别
- 令牌桶为什么适合"突发流量"
- 滑动窗口为什么比"固定窗口"更平滑
- 限流器的参数应该怎么设置

## 第三阶段：应用到实际场景

### 这一阶段学什么

- 把限流器接入到登录 API（防暴力破解）
- 把限流器接入到聊天 API（防滥用）
- 把缓存接入到用户信息查询（减少数据库压力）

### 为什么最后应用

前两个阶段把工具做好，这一阶段只是"用工具"，不会混乱。

### 代码目标

**登录限流**：
- 同一 IP 每小时最多 10 次登录尝试
- 同一用户每分钟最多 3 次登录尝试
- 超限后返回友好提示

**聊天限流**：
- 同一用户每分钟最多 30 条消息
- 超限后返回"发送太快，请稍后再试"

**用户信息缓存**：
- 缓存当前用户信息（TTL 5 分钟）
- 更新信息时主动失效缓存

### 要改的文件

```
src/app/api/auth/login/
  route.ts                    # 添加限流检查

src/app/api/chat/
  route.ts                    # 添加限流检查

src/server/auth/
  auth-service.ts             # 添加缓存失效逻辑
```

### 怎么验证

- 快速点击登录，看是否被限流
- 快速发送消息，看是否被限流
- 更新用户信息后，验证缓存是否失效

## 最该记住的句子

> 缓存是"用空间换时间"，限流是"用规则保护服务"。
>
> Redis 快是因为它在内存里，但正因为如此，它不能存所有数据。
>
> 限流不是为了阻止正常用户，而是为了防止恶意用户拖垮服务。
