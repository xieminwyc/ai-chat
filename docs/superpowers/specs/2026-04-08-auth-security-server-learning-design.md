## 背景

当前项目已经不是单纯页面练习，而是已经打通了这些能力：

- `Next.js 16 + App Router` 页面和 Route Handler
- `Prisma + PostgreSQL` 数据持久化
- 聊天主链路、流式回复、会话列表与历史记录
- `Vitest` 基础测试
- `Docker + GitHub Actions + 服务器部署`

但如果把它当成“真正的小产品训练场”，当前最明显的缺口仍然是这三块：

1. 没有正式的认证与权限边界。
2. 接口只有最基本的空值判断，缺少系统化输入校验与安全约束。
3. 首页的数据初始化和主链路仍然偏客户端思维，Next.js 服务端能力还没真正练开。

用户当前目标不是立刻做大而全业务，而是：

- 用这个项目继续学真正的全栈基础
- 明天就能开始干活
- 一边做，一边大概看懂“为什么这么做”
- 为以后接真实业务打底，而不是只把功能拼起来

因此，这份设计不追求“一次做完全部账号体系”，而是优先设计一条最适合学习和实施的主线。

## 本次设计目标

这份设计要解决 4 件事：

1. 给当前项目定义一个未来 `1 到 2` 个月的真实成长路线。
2. 明确明天开始时，只聚焦 `认证/权限`、`安全校验`、`Next.js 服务端能力` 这三块。
3. 让每个阶段同时具备：
   - 学习目标
   - 代码目标
   - 验证方式
4. 保证路线贴合当前仓库，不写成抽象教程。

## 本次设计不做

这份设计明确不把下面这些内容塞进“明天就开工”的第一阶段：

- 第三方登录
- 邮箱魔法链接
- 忘记密码 / 重置密码
- 多角色权限系统
- 后台管理系统
- 支付、文件上传、邮件投递的完整接入
- 完整游客试用与历史合并功能
- 完整可观测性平台

这些内容不是不做，而是放到后续路线里，避免第一阶段失控。

## 方案比较

### 方案 A：能力主线型，我方推荐

核心思路：

- 先按能力缺口推进，而不是按业务页面堆功能
- 明天先完成三个最关键的基础块：
  - `认证/权限`
  - `安全校验`
  - `Next.js 服务端能力`
- 每个阶段都补“你在学什么、为什么先做它、做完应该懂什么”
- 后续再把游客模式、邮箱验证、E2E、监控等能力挂到第二阶段以后

优点：

- 最适合当前“边做边学”的目标
- 能把真实全栈里最容易卡住的底层能力先补起来
- 不会让第一阶段被产品细节冲散
- 做完后，你对后续业务功能的理解会明显更稳

缺点：

- 第一阶段的用户可见功能变化不会像“直接上完整注册系统”那样大
- 需要接受“先补基础，再扩业务”的节奏

### 方案 B：产品主线型

核心思路：

- 直接按“更完整的 AI Chat 产品”来拆
- 一次性把注册登录、游客试用、聊天归属、邮箱验证、合并历史一起设计和推进

优点：

- 更像真实产品需求推进
- 用户可见功能变化更明显

缺点：

- 对当前学习阶段来说太重
- 很容易把认证、安全、Next.js 服务端原理混在一起，最后只是功能能跑

### 方案 C：理论主线型

核心思路：

- 先系统整理认证、cookie、session、权限、RSC、Server Action、校验、安全这些概念
- 之后再开始写项目计划

优点：

- 概念最稳
- 容易补知识盲区

缺点：

- 明天不够容易直接开工
- 容易再次退回“看懂了，但没真正落地”

### 推荐结论

采用 `方案 A：能力主线型`，但使用“学习版 + 项目版混合写法”。

原因：

- 它最贴合当前目标。
- 它能让你在项目里真正理解“认证、权限、安全、服务端能力”。
- 它还能自然衔接你之前已经写过的更大账号体系设计，而不需要明天一次吃掉全部复杂度。

## 总体结构设计

这次后续要写的实施计划，建议固定成下面 5 部分：

### 1. 当前能力盘点

先明确你已经会什么，避免重复学：

- TypeScript 基础已具备
- Prisma/PostgreSQL 已接入
- Route Handler 和服务端分层已开始成型
- 基础测试、CI/CD、Docker 已落地

### 2. 明天开工的核心三阶段

主线固定为：

```text
认证/权限
-> 安全校验
-> Next.js 服务端能力
```

顺序不能乱。

原因：

- 没有身份，就谈不上资源归属和权限检查
- 没有校验和安全约束，接口只是在“碰运气”
- 没有服务端边界，Next.js 的核心优势也没真正用起来

### 3. 每阶段都采用同一种写法

每个阶段都必须同时包含：

- 你在学什么
- 为什么先做它
- 代码目标是什么
- 要改哪些文件
- 怎么验证
- 做完后你应该真正懂什么

### 4. 未来路线单独挂在后面

未来路线会保留，但不抢占明天的注意力。

### 5. 全部计划都尽量用“小步可验证”的方式推进

每一阶段都要能做到：

- 范围清楚
- 文件清楚
- 验证清楚
- 出错时知道先查哪一层

## 明天开始的第一阶段设计

### 阶段 1：认证与权限基础

#### 这一阶段主要学什么

- 认证、Session、权限的区别
- 为什么“用户身份”和“聊天记录归属”必须绑起来
- 密码登录在服务端链路里是怎么成立的
- Cookie / Session 在 Next.js App Router 里如何读写

#### 为什么先做它

因为没有这一层，当前聊天数据本质上是“谁都能看、谁都能改”的思路。

你现在最需要学的不是“怎么把登录页画出来”，而是：

- 用户是谁
- 服务端怎么认出他
- 哪些聊天是他的
- 哪些请求应该被拒绝

#### 推荐实现方向

第一阶段推荐采用：

- 自己实现最小 `邮箱 + 密码 + session cookie` 方案
- 明确这是“学习版最小实现”
- 代码结构为后续迁移到 `Auth.js` 预留边界

这样设计的原因是：

- Next.js 官方也明确说自定义 auth 适合学习，但生产上通常推荐认证库
- 你当前目标先是搞懂机制，而不是立刻接入最重的现成方案

#### 第一阶段代码目标

建议只做到这些：

- 新增 `User` 和 `Session` 模型
- `Chat` 增加明确的拥有者字段
- 支持注册、登录、退出登录
- 用服务端写 `httpOnly` session cookie
- 服务端能根据 cookie 找到当前用户
- 聊天列表、聊天详情、改名、删除、发送消息都只允许访问自己的数据

#### 这一阶段暂时不做

- 邮箱验证
- 游客试用
- 游客历史合并
- 第三方登录

这些放到后续路线。

## 明天开始的第二阶段设计

### 阶段 2：安全校验基础

#### 这一阶段主要学什么

- 输入校验为什么不能只靠前端
- 为什么“字段存在”不等于“请求合法”
- 错误返回怎么统一
- 密码哈希、权限检查、最小限流分别在保护什么

#### 为什么接在认证后面

因为一旦开始接收邮箱、密码、登录请求，安全问题就不再是“以后再说”的内容了。

如果第一阶段只做了注册登录，但：

- 没有 schema 校验
- 没有密码哈希
- 没有明确错误边界
- 没有最小权限检查

那你学到的就只是“功能表面跑起来”。

#### 推荐实现方向

这一阶段建议优先补：

- `zod` 输入 schema
- 统一错误结构
- 密码哈希
- route / service 层权限校验
- 登录和注册接口的最小限流思路

其中限流第一版可以先做“最小学习版”：

- 本地内存限流即可
- 明白机制和放置位置即可
- 不要求明天就上 Redis

#### 第二阶段代码目标

- 注册和登录请求改用 schema 校验
- 聊天相关 route 的 `query/body` 改为系统化校验
- 敏感错误不直接把内部细节暴露给前端
- 密码不明文入库
- 非拥有者访问聊天时返回明确拒绝

## 明天开始的第三阶段设计

### 阶段 3：Next.js 服务端能力

#### 这一阶段主要学什么

- `page.tsx` 和 `layout.tsx` 默认就是 Server Component
- `cookies()` 在 Next.js 16 里是异步的
- Route Handler 可以写 cookie，Server Component 可以读 cookie
- 为什么“数据库查询放在 Server Component”会比“页面先加载，再客户端 fetch”更接近 Next.js 的推荐思路
- Client Component 的边界应该尽量收窄

#### 为什么放在第三步

因为只有在你已经有了：

- 用户身份
- session cookie
- 服务端鉴权逻辑

之后，把初始化数据移动到服务端才真正有意义。

否则你会变成只是机械地“把 fetch 从客户端挪到服务端”，但不理解为什么要这么挪。

#### 推荐实现方向

这一阶段建议：

- 保留交互密集的聊天 UI 为 Client Component
- 把首页入口和初始化数据读取改成 Server Component 驱动
- 让服务端先读当前 session、当前用户信息、初始聊天列表
- 需要 request-time 数据的地方明确使用 `cookies()`

#### 第三阶段代码目标

- `src/app/page.tsx` 变成真正的服务端入口
- 初始聊天列表和当前用户信息尽量在服务端准备好
- Client Component 只接收必要初始数据并负责交互
- 对 `cookies()`、动态渲染、客户端边界有一次清晰实践

## 未来路线设计

第一阶段做完后，后续推荐按这个顺序继续：

### 第四阶段：游客试用、邮箱验证与历史合并

对应已有设计文档里的更完整账号体系方向。

### 第五阶段：认证体系加固

包括：

- middleware 或页面保护策略
- 更清楚的 session 过期策略
- 账号安全细节
- 更好的错误日志

### 第六阶段：测试与可观测性

包括：

- Playwright E2E
- 登录态相关测试
- 错误监控
- 服务端日志分层

### 第七阶段：更像真实产品的配套能力

包括：

- 邮件发送
- 文件上传
- 额度与计费雏形
- 后台管理入口

## 成功标准

这份设计对应的后续实施计划，至少要满足这些标准：

1. 明天可以直接开工，不需要再重新拆范围。
2. 计划主线始终围绕三块核心缺口，不被其他需求打散。
3. 每一阶段都同时解释“学什么”和“做什么”。
4. 计划里的文件路径要尽量明确，能落回当前仓库。
5. 第一阶段完成后，你应该不只是会抄功能，而是能说清楚：
   - 认证是什么
   - Session 是怎么工作的
   - 权限为什么必须在服务端兜底
   - 为什么 Next.js 要把一部分数据读取放在服务端

## 最终结论

这次路线最终采用：

```text
能力主线型
+ 学习/项目混合写法
+ 明天只做：
认证/权限 -> 安全校验 -> Next.js 服务端能力
```

这样安排最适合当前项目和当前学习目标。

它不会让你明天一上来就被复杂产品需求压住，但又能保证你学到的是以后做真实业务时最常用、最值钱的那一层。
