# AI Chat Forgot Password And Reset Flow Design

## 文档概览

| 项目 | 内容 |
| --- | --- |
| 文档主题 | 为登录流程增加完整最小闭环的忘记密码能力 |
| 当前阶段 | auth 能力从注册 / 登录 / 验证邮件扩展到密码找回 |
| 推荐方向 | 登录面板增加“忘记密码？”入口，配合 reset token + 邮件 + `/reset-password` 页面 |
| 目标 | 让用户可以通过邮箱安全地重置密码，同时不暴露邮箱是否已注册 |

## 背景

当前项目已经具备：

- 注册
- 登录
- 邮箱验证
- 重新发送验证邮件
- verified-only 修改密码

现在 auth 体系里最明显的缺口之一，就是“忘记密码”。如果用户既没登录、又忘了原密码，当前系统没有一条正式恢复链路。

## 这次要解决什么

这次只解决一条最小但完整的找回密码闭环：

1. 登录表单里提供“忘记密码？”入口
2. 用户提交邮箱后，系统在后台判断是否存在对应用户
3. 如果存在，就生成一次性 reset token 并发送重置邮件
4. 用户打开 `/reset-password?token=...`
5. 用户设置新密码
6. token 被标记为已使用，旧密码失效

这次**不**做：

- 短信找回
- 多因素身份验证
- 验证码节流 / 频率限制高级版
- 修改邮箱

## 核心安全边界

这是这次设计里最重要的一点：

### 服务端内部

- 必须校验邮箱是否存在对应用户
- 只有存在用户时，才生成 reset token 和发送邮件

### 前端外部

- 不暴露“邮箱不存在”
- 无论该邮箱是否存在，都返回统一成功提示

推荐提示：

> 如果该邮箱已注册，我们会向你发送重置密码邮件。

原因很明确：

- 如果直接提示“邮箱不存在”，就会暴露系统里哪些邮箱注册过
- 这会形成用户枚举风险

所以正确做法不是“不校验邮箱”，而是：

> 后端必须校验，但前端不应泄露校验结果。

## 方案对比

### 方案 A：只做登录页入口占位

优点：

- 快

缺点：

- 没有真实恢复能力

### 方案 B：完整最小闭环，我方推荐

做法：

- 登录处提供入口
- 后端生成 reset token
- 邮件里给 reset link
- 新增 `/reset-password` 页面完成新密码设置

优点：

- 这是一个真正可用的 auth 恢复链路
- 与当前邮箱验证体系非常一致
- 学习价值高，能把 token + mail + reset 这条链一次跑通

缺点：

- 会新增 token 模型和 2 个 route

### 推荐结论

采用方案 B。

## 页面与交互设计

### 1. 登录面板

在当前登录表单里增加：

- `忘记密码？`

点击后切到一个很小的 forgot-password 视图：

- 输入邮箱
- 提交后显示统一成功提示
- 提供返回登录入口

### 2. Reset Password 页面

新增：

- `/reset-password`

行为：

- 从 URL 读取 `token`
- 没有 token：显示失败态
- 有 token：展示新密码 / 确认新密码表单
- 提交成功后显示成功提示，并引导用户回登录

## 后端设计

### 新增 reset token 能力

需要一条与邮箱验证 token 类似、但用途不同的链路：

- 创建 reset token
- hash 后保存
- 通过 hash 查询
- 标记为 used
- 清理同用户未使用旧 token

### 新增接口

#### `POST /api/auth/forgot-password`

输入：

- `email`

行为：

- 校验 payload
- 查用户是否存在
- 存在则生成 token 并发送邮件
- 不存在则不发邮件
- 无论是否存在，都返回统一成功响应

#### `POST /api/auth/reset-password`

输入：

- `token`
- `nextPassword`
- `confirmPassword`

行为：

- 校验 payload
- 校验 token 存在、未使用、未过期
- hash 新密码
- 更新用户密码
- 标记 token 已使用

## 技术分工

### route

负责：

- payload 校验
- response status
- 调 service

### service

负责：

- 用户存在性判断
- token 生成 / 查验 / 失效判断
- 新密码写入
- 安全规则

### repository

负责：

- token 持久化
- 查库
- 标记 used
- 更新密码 hash

## 测试策略

### forgot-password route / service

覆盖：

- 邮箱存在时会创建 token 并触发邮件发送
- 邮箱不存在时不发邮件，但仍返回统一成功响应

### reset-password route / service

覆盖：

- token 不存在或已使用时失败
- token 过期时失败
- 新密码确认不一致时失败
- 成功时更新密码并消费 token

### 页面 / 前端

覆盖：

- 登录处出现“忘记密码？”入口
- forgot-password 视图能提交邮箱并显示统一提示
- `/reset-password` 页面成功与失败状态

## 学习重点

这一步最值得学习的是：

1. 为什么“内部校验”和“外部反馈”要分开
2. reset token 链路和 email verification token 链路有什么共性
3. 为什么敏感恢复流程一定要走一次性 token，而不是直接改密码

## 后续延伸

这一步完成后，后面可以继续扩展：

- token 申请频率限制
- reset 成功后清理旧 session
- 更完整的安全审计与通知
