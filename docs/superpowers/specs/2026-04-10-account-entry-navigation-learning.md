# AI Chat Account Entry Navigation Learning Notes

## 这一步在练什么

这一步表面上只是“给 `/account` 和 `/settings` 加入口”，但本质上在练 3 件事：

1. 前端入口设计
2. 服务端权限边界的产品化表达
3. 工作台型界面里，导航和主任务区如何分层

## 为什么不是把入口丢到左侧聊天栏

因为左侧现在的主职责很清楚：

- 展示历史会话
- 支持切换会话xieminstudio.xyz
- 承担“内容导航”

而 `/account` 与 `/settings` 属于“身份与设置导航”。如果把它们塞进左侧，会把“聊天对象导航”和“账号导航”混成一层，用户会更难形成稳定心智模型。

所以更合理的位置是右上角用户区：xieminstudio.xyz

- 这里本来就在表达“当前是谁”
- 自然适合承接“这个用户还能去哪里”

## 为什么未验证用户也要看见 Settings

如果未验证时直接把 `Settings` 完全隐藏，会产生两个问题：

1. 用户不知道还有这个能力
2. 用户会把“没入口”误解成“系统没有这个页面”

因此更好的表达是：

- 保留可见性
- 明确限制原因
- 把限制和状态关联起来

也就是：

- 你可以看到 Settings
- 但因为邮箱未验证，现在还不能进入

这比“直接消失”更符合真实产品的反馈方式。

## 这一层和服务端保护是什么关系

要分清两层：

### 第一层：前端入口表达

这层解决：

- 页面有没有入口
- 入口显示成什么状态
- 用户是否能理解限制原因

### 第二层：服务端页面保护

这层解决：

- 用户直接访问 URL 时能不能进入
- 未满足条件时是否重定向

所以即使前端把 `Settings` 弱化成不可点，服务端页面保护仍然必须存在。前端入口只是“表达规则”，不是“替代规则”。

## 这一步最该记住的句子

可以这样记：

> 前端导航负责让规则被看见，服务端保护负责让规则真正成立。

## 下一步自然会接什么

这一步完成后，后面最自然的演进有两种：

1. 给 `/account` 和 `/settings` 做真实内容
2. 如果受保护页面继续变多，再考虑抽更统一的导航或轻量 `proxy.ts`

也就是说，这一步不是在做“最终导航系统”，而是在把已有权限模型第一次真实地放到界面里。
